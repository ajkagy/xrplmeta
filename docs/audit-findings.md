# Codebase Audit Findings

_Generated by an 11-area multi-agent audit (74 agents); every finding adversarially verified against the real code. 56 confirmed + 12 cross-cutting (critic). Items marked ✅ FIXED were addressed in the same session; all 78 unit tests pass._


## CRITICAL (3)

### [security/bootstrap-lib] SSRF: TOML/domain crawler fetches issuer-controlled domains with no URL validation — ✅ FIXED
- **File:** `src/crawl/crawlers/domains.js` 24-26, 148-168  (verdict: confirmed)
- **What:** The domains crawler builds a fetch client with createFetch({ timeout }) but does NOT pass validateUrls: true. It then fetches `${protocol}//${host}${pathname}/.well-known/xrp-ledger.toml` where `host`/`protocol` come from the on-ledger token issuer `domain` property (fully attacker-controlled — anyone can issue a token and set its domain). Because validateUrls is false, fetchWithSafeRedirects() never calls validate(), so the indexer will happily fetch internal/loopback/cloud-metadata endpoints.
- **Fix:** Create the fetch client with `createFetch({ timeout, validateUrls: true })` in domains.js. Note that validate() only blocks IP-literal hosts; a hostname that DNS-resolves to a private IP still passes (see DNS-rebinding finding), so additionally resolve the host and re-check the resolved address, or run the crawler in a network-egress-restricted sandbox.

### [bug/db-helpers] AMM read helpers crash: ammPools table is never registered (definition unreferenced in core.json properties) — ✅ FIXED
- **File:** `src/db/helpers/amm.js` 17-28, 56, 106  (verdict: confirmed)
- **What:** All three AMM read helpers (readAmmPools, readAmmPoolByAccount, readAmmPoolSeries) access ctx.db.core.ammPools, but that table model is never created, so ctx.db.core.ammPools is undefined and every call throws 'Cannot read properties of undefined (reading readMany/readOne/count)'. structdb builds its table set by walking the ROOT `properties` block of the schema (vendor/structdb/struct.js:16 `generate`/`walk` iterates schema.properties). In src/db/schemas/core.json the `properties` object (lines 4-119) lists tables only up to `mptokenMetadataUpdates`; it has NO `ammPools` (nor `vaults`/`oracles`) entry. The `AmmPool` object exists only under `definitions` (core.json:858) and is referenced by nothing in `properties`, so no model/table is generated.
- **Fix:** Register the AMM (and Vault/Oracle) tables by adding the corresponding array entries to the root `properties` block of core.json, e.g. `"ammPools": { "type": "array", "items": { "$ref": "#/definitions/AmmPool" } }` (and likewise `vaults`->Vault, `oracles`->Oracle, `unknownLedgerEntryTypes`->UnknownLedgerEntryType). Without this the entire AMM API surface is dead. Optionally also add the same defensive `if(!ctx.db?.core?.ammPools)` guard used on the writer side so the readers degrade gracefully instead of throwing.

### [bug/server-api] WS client cleanup uses splice() with no deleteCount — drops all later clients, leaking sockets — ✅ FIXED
- **File:** `src/srv/ws.js` 149-153  (verdict: confirmed)
- **What:** On socket 'close', the handler runs clients.splice(clients.indexOf(client)). Array.prototype.splice with a single argument removes EVERY element from that index to the end of the array, not just the one client. So when any client disconnects, all clients registered after it are silently removed from the `clients` array while their underlying sockets stay open and registered with the event-loop.
- **Fix:** Use clients.splice(clients.indexOf(client), 1). Guard against indexOf === -1 (don't splice when not found, since splice(-1,1) would wrongly drop the last element).


## HIGH (12)

### [security/bootstrap-lib] Icon download bypasses all byte bounds (raw:true + arrayBuffer) — memory-exhaustion DoS — ✅ FIXED
- **File:** `src/cache/icons.js` 244-252  (verdict: confirmed)
- **What:** downloadAndProcessIcon fetches with `{ raw: true }`, which makes createFetch return the bare Response (fetch.js:48-49) and skips readBytesBounded entirely. It then does `Buffer.from(await res.arrayBuffer())` with no size cap. The icon URL is issuer-controlled, so a malicious/compromised host can return a multi-GB body (or a chunked stream with no content-length) and the node buffers it all into memory, then hands it to sharp. This defeats the DEFAULT_MAX_BYTES.binary protection that exists precisely for this path.
- **Fix:** Do not use raw:true for icon downloads; instead let createFetch route through readBytesBounded (binary branch) and return the bounded Buffer, or add an explicit content-length check plus a streamed size cap before arrayBuffer(). Reject responses exceeding limits.binary.

### [security/bootstrap-lib] SSRF URL validation runs before DNS resolution — vulnerable to DNS rebinding
- **File:** `src/lib/url.js` 20-52  (verdict: confirmed)
- **What:** validate() only inspects the textual hostname: it blocks IP literals and a few suffixes, but any normal hostname (not an IP literal) returns true at url.js:51. The subsequent fetch() resolves DNS independently, so an attacker-controlled domain whose A record points at 127.0.0.1 / 10.x / 169.254.169.254 passes validation and is then fetched against the private address. validateUrls:true (used by icons.js) therefore does not actually prevent SSRF to internal hosts reached via a public hostname.
- **Fix:** Resolve the hostname (dns.lookup with all addresses) and validate every resolved IP against isPrivateIPv4/isPrivateIPv6 before connecting, then pin the connection to that vetted IP (custom lookup/agent) so the address can't change between validation and connect. Re-validate after each redirect hop.

### [bug/cache] unlinkCachedIconFromTokenCache reads wrong field (cachedIcon vs cachedIcons), wiping all other cached icons — ✅ FIXED
- **File:** `src/cache/icons.js` 225-235  (verdict: confirmed)
- **What:** When an icon URL is no longer used by a token, unlinkCachedIconFromTokenCache spreads `tokenCache.cachedIcon` (singular) before deleting the one URL. The schema field is `cachedIcons` (plural) — see src/db/schemas/cache.json:80. `tokenCache.cachedIcon` is always undefined, so spreading it contributes nothing, and the resulting update writes `{ [url]: undefined }` as the ENTIRE cachedIcons object. Every other cached icon mapping for that token is silently dropped.
- **Fix:** Change `...tokenCache.cachedIcon` to `...tokenCache.cachedIcons` on line 228 so the existing icon map is preserved and only the removed URL key is cleared.

### [security/cache] Icon download bypasses byte-size limits (raw fetch + unbounded arrayBuffer) — memory-exhaustion DoS — ✅ FIXED
- **File:** `src/cache/icons.js` 244-252  (verdict: confirmed)
- **What:** downloadAndProcessIcon fetches with `{ raw: true }`, which makes createFetch return the underlying Response immediately (src/lib/fetch.js:48-49) WITHOUT applying readBytesBounded. The code then does `Buffer.from(await res.arrayBuffer())` with no size cap, so the DEFAULT_MAX_BYTES.binary (10 MiB) guard is never enforced. Icon URLs come from token/account props (attacker-controllable on-ledger metadata). A malicious issuer can point an `icon` prop at a multi-GB endpoint and exhaust the cache worker's memory; the decoded buffer is then handed to sharp and resized 4x (image-bomb amplification).
- **Fix:** Do not use raw mode for downloads. Either drop `{ raw: true }` and use the binary path (readBytesBounded enforces 10 MiB + content-length check), or in the raw branch stream the body through a bounded reader / check `content-length` and abort over a max-bytes threshold before calling arrayBuffer().

### [security/crawlers] SSRF: domains crawler fetches arbitrary user-controlled domains without validateUrls — ✅ FIXED
- **File:** `src/crawl/crawlers/domains.js` 24-26, 148-189  (verdict: confirmed)
- **What:** The domains crawler resolves each issuer's `domain` prop (which originates from on-ledger account data / external trustlists and is fully attacker-controlled) and fetches `https://<domain>/.well-known/xrp-ledger.toml`. It creates the fetch client with `createFetch({ timeout: config.connectionTimeout || 20 })` and never passes `validateUrls: true`. In src/lib/fetch.js, `validateUrls` defaults to false (line 12), so the SSRF hostname guard in src/lib/url.js (`validate()`, which blocks localhost, 127.0.0.0/8, 169.254.169.254 cloud-metadata, RFC1918, IPv6 ULA/link-local, etc.) is never invoked for this crawler. An attacker who controls an issuer account can set its domain to `http://169.254.169.254/...` or `http://127.0.0.1:<port>/...` and the indexer will fetch internal endpoints, following redirects too (fetchWithSafeRedirects only validates when validateUrls is on).
- **Fix:** Create the domains fetch client with `createFetch({ timeout: ..., validateUrls: true })` so both the initial URL and every redirect hop are checked against url.js `validate()` before the network request, matching the icons.js pattern.

### [bug/crawlers] scheduleBatchedIterator marks items done even when commit() throws, dropping failed batches until next full interval — ✅ FIXED
- **File:** `src/crawl/schedule.js` 176-200  (verdict: confirmed)
- **What:** In `flush()`, `commit(batch)` is wrapped in try/catch that only logs the error (lines 179-184). After the catch, the code UNCONDITIONALLY writes an `operations` row for every item in the batch (lines 186-199), marking them processed for this `interval`. So if a commit fails (HTTP non-200, rate-limit, network error, malformed response — e.g. x.js commit throws `HTTP ${status}` on line 119 or `errors[0]` on line 122), those items are still recorded as done and will NOT be retried until the entire `fetchInterval` elapses. A single transient X API failure silently abandons up to `batchSize` (100) tokens for a full cycle, causing missing/stale data.
- **Fix:** Only write the operations rows on success. Move the mark-done loop inside the try block after `await commit(batch)`, or set a `let ok = true` flag, set `ok = false` in catch, and guard the loop with `if(ok)`. Failed batches then remain un-marked and are retried on the next iteration / sooner than a full interval.

### [security/db-helpers] Unbounded `points` in readAmmPoolSeries causes event-loop-blocking O(span) synchronous loop (DoS) — ✅ FIXED
- **File:** `src/db/helpers/amm.js` 105-152  (verdict: confirmed)
- **What:** readAmmPoolSeries derives the sample step from caller-supplied `points`: `step = Math.max(1, Math.floor(span / Math.max(1, points - 1)))`. When `points` is large, `step` collapses to 1 and the loop `for(let seq = startSeq; seq <= endSeq; seq += step)` iterates over the ENTIRE ledger span (potentially millions of ledgers), performing two synchronous better-sqlite3 point queries (readBalance) per iteration. better-sqlite3 is synchronous, so this fully blocks the Node event loop for the whole request, starving all other clients.
- **Fix:** Clamp `points` inside readAmmPoolSeries (e.g. `points = Math.min(Math.max(1, points|0), 1000)`) and/or add a sanitizer for it on the amm_series route mirroring sanitizeLimitOffset's maxLimit pattern. The loop length must be capped by `points`, never by the raw ledger span.

### [bug/ledger-state] MPToken empty-PreviousFields heuristic can double-count holders/supply when MPTAmount did not actually change
- **File:** `src/ledger/state/index.js` 144-147  (verdict: confirmed)
- **What:** For a ModifiedNode of type MPToken with an empty PreviousFields, the code unconditionally forces `previous.MPTAmount = '0'`. The comment assumes empty PreviousFields always means the prior balance was the default 0. But an MPToken ModifiedNode can have empty PreviousFields for other reasons (e.g. only the object's directory linkage / metadata changed, or a flag whose previous value was the default toggled). In those cases MPTAmount is unchanged and non-zero, yet this code makes `previous.MPTAmount=0` while final.MPTAmount=X. mptoken.diff then computes supply += (X-0) and increments holders (eq(previous,0)&&gt(final,0)), permanently inflating supply and holder count.
- **Fix:** Only inject MPTAmount='0' when FinalFields actually contains a non-default MPTAmount AND PreviousFields lacks it specifically — i.e. gate on `ModifiedNode.FinalFields?.MPTAmount != null && ModifiedNode.PreviousFields?.MPTAmount === undefined`, and otherwise leave previous.MPTAmount equal to final so the diff is a no-op. Better: detect the genuine 0->X case by checking that FinalFields.MPTAmount is present and PreviousFields is empty, but skip when no balance-bearing field is present at all.

### [bug/server-api] tokens_subscribe_v1/unsubscribe never actually tagged mustRunMainThread — routed to worker without ctx.client, crashing — ✅ FIXED
- **File:** `src/srv/api.js` 72-83, 167-176  (verdict: confirmed)
- **What:** subscribe/unsubscribe rely on ctx.client (per-connection subscription map). They try to force main-thread execution via tag({ mustRunMainThread: true }) placed as the last element of the compose() chain. But compose() reduces left-to-right calling each element on the running VALUE, so tag() is invoked with the response object, not the procedure function. It assigns mustRunMainThread onto the RESPONSE, never onto the exported procedure function. Therefore executeProcedure() sees func.mustRunMainThread === undefined and dispatches to a worker.
- **Fix:** Tag the composed export directly, e.g. make compose accept options or do `Object.assign(tokens_subscribe_v1, { mustRunMainThread: true })` after composing. Remove the no-op tag() step from the chain. Add a test that calls the WS subscribe command end-to-end.

### [efficiency/server-api] Token list endpoints allow limit up to 100000, reading 100k rows synchronously and blocking the event loop
- **File:** `src/srv/api.js` 33, 44, 53, 63, 131, 139  (verdict: confirmed)
- **What:** tokens/iou_tokens/mpt_tokens/token_holders all use sanitizeLimitOffset({ defaultLimit: 100, maxLimit: 100000 }). better-sqlite3 is fully synchronous and (per worker.js) runs on the same process event loop. A single request with limit=100000 forces serveTokenList to readMany 100k cache rows AND run formatTokenCache (reduceProps, icon URL building, BigInt .toString()) for each, all synchronously, stalling the loop for seconds. Load-shedding (isLoopCritical) only triggers AFTER lag is already >2s, so the first such request still blocks everything; concurrent ones get 503 but the damage is done.
- **Fix:** Lower maxLimit to a sane page size (e.g. 1000) for list/holders endpoints, matching exchanges (1000). If large exports are required, paginate with a marker or stream. At minimum cap maxLimit well below the point where a single request can stall the loop.

### [bug/xfl-math] canonicalize() flips the sign of negative values on exponent underflow — ✅ FIXED
- **File:** `vendor/xfl/canonical.js` 30-33  (verdict: confirmed)
- **What:** When a value's exponent falls below exponentMin (-96), the clamp branch sets xfl.mantissa = mantissaMin, which is the POSITIVE constant 1000000000000000n, regardless of the original sign. A tiny negative number is therefore clamped to a tiny POSITIVE number — the sign is corrupted. The overflow branch (exponent > exponentMax) has the same flaw, setting mantissa = mantissaMax (positive) for negatives. mantissaMin/mantissaMax are defined as unsigned magnitudes in constants.js (lines 1-2).
- **Fix:** Capture sign before clamping and reapply: in the underflow branch set `xfl.mantissa = mantissaMin * sign`, and in the overflow branch `xfl.mantissa = mantissaMax * sign` (sign is already computed at line 11). This preserves the value's sign at the representable boundary.

### [bug/xrpl-protocol] MPT issuance-id case mismatch: lowercase trustlist ids never match uppercase ledger ids — ✅ FIXED
- **File:** `src/xrpl/mpt.js` 3-5, 12-19  (verdict: confirmed)
- **What:** The ledger path stores MPT ids as UPPERCASE: `mptIssuanceIdFromIssuerAndSequence` ends with `.toUpperCase()` (mpt.js:19), and that value is written to the unique `tokens.mptIssuanceId` column (ledger/state/mptokenissuance.js:22). The trustlist path, however, stores the `mpt_issuance_id` string verbatim from the TOML (crawl/crawlers/trustlists.js:104 `mptIssuanceId: mpt_issuance_id`), and the XLS-26 schema explicitly accepts lowercase hex (`/^[0-9a-fA-F]{48}$/`, xls26.js:183). `tokens.mptIssuanceId` is a unique TEXT column (db/schemas/core.json:385,408) and SQLite TEXT comparison is case-sensitive by default, so a lowercase trustlist id and the uppercase ledger id are two distinct keys. A trustlist that uses lowercase therefore either creates a duplicate token row or attaches its trust_level/metadata to a token that never joins the real ledger token. Separately, `isValidMPTIssuanceId` (mpt.js:3-5) uses `/^[A-Z0-9]{48}$/`, which rejects a perfectly valid lowercase id supplied by an API client.
- **Fix:** Canonicalize MPT ids to uppercase at every ingress: uppercase `mpt_issuance_id` in the trustlist crawler before storing, and in `parseMPT`/`isValidMPTIssuanceId` accept `[0-9a-fA-F]{48}` (case-insensitive) then uppercase before the DB lookup. Alternatively store mptIssuanceId with a NOCASE collation.


## MEDIUM (13)

### [security/cache] SSRF: URL validation is hostname-string-based and vulnerable to DNS rebinding for icon fetches
- **File:** `src/lib/url.js` 20-52  (verdict: confirmed)
- **What:** validate() only inspects the hostname string. For non-IP-literal hostnames it returns true without resolving DNS. The icon fetch path (icons.js, createFetch({ validateUrls: true })) therefore allows an attacker-controlled hostname that resolves to a private/link-local address (e.g. a domain whose A record is 169.254.169.254, the cloud metadata endpoint) to pass validation on every redirect hop and then be fetched by node fetch, which resolves DNS independently. Each redirect is re-validated against the string but never against the resolved IP, so DNS rebinding between validate() and fetch() is unguarded.
- **Fix:** Resolve the hostname (dns.lookup with { all: true }) and run isPrivateIPv4/isPrivateIPv6 against every resolved address before connecting, or use a fetch agent with a lookup hook that rejects private IPs at connect time. Apply on each redirect hop in fetchWithSafeRedirects.

### [bug/ledger-derived] Marketcap double-written with divergent prices when a token has both an exchange and a supply change in the same ledger
- **File:** `src/ledger/derived/index.js` 4-12  (verdict: confirmed)
- **What:** updateDerived iterates newItems.tokenExchanges then newItems.tokenSupply. For a token that has BOTH a new exchange and a supply change in the same ledger, updateMarketcapFromExchange and updateMarketcapFromSupply both write the same (token, ledgerSequence) tokenMarketcap point, but compute the price from different sources. updateMarketcapFromExchange (marketcap.js:53-73) uses the just-inserted exchange's raw price (no dust filtering). updateMarketcapFromSupply (marketcap.js:76-99) calls readTokenExchangeAligned with skipDust:true, which may pick a DIFFERENT (older, non-dust) exchange. Because tokenSupply is processed after tokenExchanges, the supply path always overwrites the exchange path, so the dust-skipping branch silently wins and the result depends on table iteration order rather than intent.
- **Fix:** Pick a single source of truth for marketcap per (token, ledgerSequence). Either (a) only derive marketcap from supply changes and from exchanges-without-supply-change, deduping by token within the ledger, or (b) collect the set of affected tokens first, then compute marketcap once per token using one consistent price-selection rule (consistent skipDust behavior). At minimum, make the two code paths agree on dust handling so the write order no longer changes the result.

### [bug/ledger-derived] Off-by-one in backwards marketcap backfill overwrites an already-correct boundary marketcap point
- **File:** `src/ledger/derived/marketcap.js` 20-52  (verdict: confirmed)
- **What:** In the ctx.backwards branch, firstMarketcap is the earliest existing marketcap at ledgerSequence >= ctx.ledgerSequence, and the supply series is read with sequenceEnd = firstMarketcap.ledgerSequence using lessOrEqual (tokenmetrics.js:62-64). The loop then writes a backfilled marketcap for EVERY supply point in [ctx.ledgerSequence, firstMarketcap.ledgerSequence] INCLUSIVE. If a supply point coincides with firstMarketcap.ledgerSequence (the boundary that already had a correct marketcap), the loop clobbers that existing point with the older backfilled exchange price. The boundary should be exclusive.
- **Fix:** Use an exclusive upper bound for the backfill range — e.g. add a `lessThan` option to readTokenMetricSeries (or pass firstMarketcap.ledgerSequence - 1) so the boundary sequence that already holds a forward-computed marketcap is not overwritten.

### [bug/ledger-state] Backwards backfill never persists pseudo-account flag, causing AMM/Vault liquidity to be miscounted as holders
- **File:** `src/ledger/state/accounts.js` 61-77  (verdict: confirmed)
- **What:** In accounts.diff, when ctx.backwards is set the AccountRoot is written with only `{ address }` and the parsed `pseudo`/`pseudoSource` meta is discarded. During a backwards backfill the Account row for an AMM (LSF_AMM) or Vault pseudo-account is therefore created in the DB WITHOUT pseudo=true. pseudoAccountInfo() falls back to `ctx.db.core.accounts.readOne(...)?.pseudo` for any delta not in the current ledger's pre-scan, so trustline/MPToken diffs processed in earlier ledgers (which come later in backwards order) see pseudo=false and increment `holders` for the pool's locked liquidity. This corrupts holder counts specifically on the backfill path.
- **Fix:** On the backwards branch still persist the pseudo attribution, e.g. write `{ address, ...(meta.pseudo ? { pseudo: true, pseudoSource: meta.pseudoSource } : {}) }`, or merge override.pseudo into the backwards create the same way the forward branch does at lines 56-59. The vault.js diff already persists pseudoSource='vault' unconditionally; accounts.js should not silently drop it on backwards.

### [bug/ledger-state] issuer_name ordering update uses mismatched comparison operators against null row fields — ✅ FIXED
- **File:** `src/ledger/state/mptokenissuance.js` 56-62  (verdict: confirmed)
- **What:** The block that records the latest metadata-update ledger position compares ledgerSequence with `>=` but transactionIndex with `>`: `if (ledgerSequence >= row.ledgerSequence && transactionIndex > row.transactionIndex)`. For an existing row being updated by a strictly-newer transaction that happens to sit at transactionIndex 0 in its ledger, `transactionIndex > row.transactionIndex` is false (0 > N), so the row's stored position is NOT advanced and a stale earlier update can win the issuer_name selection. The comparison should be lexicographic on (ledgerSequence, transactionIndex), not an AND of two independent inequalities. Additionally, on a freshly created row both fields are null, so `ledgerSequence >= null` coerces to `>= 0` and `transactionIndex > null` to `> 0`, making the branch silently depend on transactionIndex being positive.
- **Fix:** Replace with a proper tuple comparison, e.g. `if(row.ledgerSequence == null || ledgerSequence > row.ledgerSequence || (ledgerSequence === row.ledgerSequence && transactionIndex > row.transactionIndex)) { row.ledgerSequence = ledgerSequence; row.transactionIndex = transactionIndex }`.

### [bug/ledger-sync] Live ledger assembly in the node pool can corrupt ledgers via a shared mutable buffer across connections
- **File:** `src/xrpl/nodepool.js` 107-124  (verdict: confirmed)
- **What:** The pool reconstructs each live ledger from individual stream events using a single closure-scoped `latestLedger` shared across ALL node connections, gated only by a global `seenHashes` dedup. A `ledgerClosed` event resets `latestLedger = {...ledger, transactions: []}`, then `transaction` events are pushed until `transactions.length === txn_count`. With multiple connections (or one connection where a new `ledgerClosed` arrives before the previous ledger's txs all arrive), `latestLedger` is overwritten mid-assembly: txs belonging to ledger N can land in ledger N+1's buffer, and the `length === txn_count` check can match on the wrong set, emitting a ledger with mismatched/duplicated transactions. Because `seenHashes` dedups globally, a tx legitimately belonging to two assembly attempts is dropped from one, so the count can also never reach `txn_count` and that ledger is never emitted.
- **Fix:** Buffer by ledger sequence (a map keyed on ledger_index) and only attach a tx to the ledger whose ledger_index it carries; emit when that specific ledger's tx set is complete, with a timeout/cleanup for incomplete ones. Mitigating factor: the forward filler re-fetches every ledger by sequence (stream.js:48), so a corrupt live-pushed ledger is dangerous only if `next()` consumes it before the authoritative fetch overwrites it via `put()`.

### [bug/server-api] sanitizeLimitOffset does not validate parseInt results — NaN/negative limit & offset reach the query builder — ✅ FIXED
- **File:** `src/srv/sanitizers/common.js` 127-140  (verdict: confirmed)
- **What:** limit is `limit ? Math.min(parseInt(limit), maxLimit) : defaultLimit` and offset is `offset ? parseInt(offset) : undefined`. parseInt of a non-numeric query value yields NaN; Math.min(NaN, maxLimit) is NaN, which flows into take/skip of the ORM. Negative values (e.g. limit=-1, offset=-5) pass through unchecked. Unlike the HTTP layer's safeInt (http.js:545) which validates ranges for sequence/time, limit/offset get no such validation, so behavior on bad input is undefined (depends on ORM/SQLite coercion of NaN/negative LIMIT/OFFSET).
- **Fix:** Validate with a helper like safeInt: parse, require Number.isFinite and >= 0, clamp limit to [1, maxLimit], default when missing; reject (400 invalidParam) otherwise. Handle limit=0 explicitly if a zero page should be allowed.

### [improvement/server-api] Worker dispatch picks ranking.at(0) even when every worker is busy — no real backpressure
- **File:** `src/srv/worker.js` 20-47, 49-63  (verdict: confirmed)
- **What:** spawnWorkers uses the in-process spawn() (lib/workers.js) which is a dynamic import, NOT a separate thread — runWorker runs in the same process/event loop. So 'workers' do not provide parallelism for synchronous better-sqlite3 work; they only round-robin. executeProcedure scores workers and always takes ranking.at(0) even when all are busy (busy subtracts 1e9 from score but a worker is still selected), so requests are not actually queued or rejected on saturation — they just pile onto the same loop. The busy flag and ranking give a false impression of isolation/concurrency.
- **Fix:** Either (a) move workers to real worker_threads so synchronous SQLite is off the main loop, or (b) drop the worker abstraction and rely solely on the isLoopCritical load-shedding, and document that procedures run on the main loop. If keeping the pool, add a queue/limit so a saturated pool applies backpressure (503) instead of overloading the single loop.

### [efficiency/structdb] Statement cache grows unbounded with variable-length IN() lists
- **File:** `vendor/structdb/adapters/better-sqlite3.js` 9, 30-46  (verdict: confirmed)
- **What:** statementCache is a plain object with no size cap or eviction; every distinct SQL string is prepared once and kept for the connection's lifetime. composeFilter renders IN() as N literal '?' placeholders equal to the deduped list length (model/common.js:222-228), so each different IN-list cardinality yields a distinct SQL string and therefore a distinct, permanently-retained prepared statement. Workloads that issue IN() with widely varying list sizes (e.g. the chunked prop sweeps, icon tasks, API trust_levels filters) accumulate a new compiled statement per distinct length, leaking memory and SQLite prepared-statement handles over the process lifetime.
- **Fix:** Either (a) bound the cache with an LRU and finalize evicted statements, or (b) make IN() lists produce a stable SQL shape — e.g. bind the array via a JSON/carray and use `IN (SELECT value FROM json_each(?))`, which yields one cached statement regardless of list size and also sidesteps the variable limit (see next finding).

### [bug/structdb] createOne ignores the computed unique WHERE and re-reads with the full input (double-read / wrong existence check)
- **File:** `vendor/structdb/model/operations/create.js` 72-104  (verdict: confirmed)
- **What:** createOne computes a precise existence filter via pullUniques()+unflatten() into `where` (lines 72-75) but then never uses it — the existence read at line 77-82 passes `where: inputData` (the entire raw input, including non-unique fields and nested objects) instead. This means: (1) the carefully-built unique-key lookup is dead code; (2) existence is decided by matching ALL input fields rather than the unique constraint, so an INSERT can still hit a UNIQUE conflict that the pre-read failed to detect (the row exists with the same unique key but a different non-unique field), and conversely an unnecessary full-input read runs on every create. After the insert it then does a second read (line 96-104) to materialize the row — so createOne performs two SELECTs plus the upsert per call.
- **Fix:** Use the computed unique `where` for the existence pre-read: `read({ database, struct, where, take: -1 })`. That both fixes the existence semantics (match on unique keys, consistent with the upcoming ON CONFLICT) and avoids encoding/matching nested input objects.

### [bug/structdb] makeRowIntegerSafe only bounds the positive side — large negative bigints become lossy Numbers — ✅ FIXED
- **File:** `vendor/structdb/model/operations/read.js` 180-187  (verdict: confirmed)
- **What:** With defaultSafeIntegers(true) every integer column is read as a bigint. makeRowIntegerSafe downcasts to Number only checking `value < 9007199254740991n` (upper bound) with no lower bound. Two iterates representing the same mathematical value but with different non-canonical (mantissa, exponent) pairs will not be eq, so convergence detection depends on bit-identical representations. The rm2 oscillation guard prevents a true infinite loop, but the loop can stop one step early/late and the final non-canonical result is only canonicalized later by the wrapper.
- **Fix:** Canonicalize each iterate before comparing (canonicalize(r) inside the loop) so eq() compares the unique canonical form, making convergence well-defined. Alternatively, compare via a tolerance on the difference rather than structural equality.

### [security/xrpl-protocol] validUrlRegex alternation precedence makes URL validation nearly a no-op
- **File:** `vendor/xls26/xls26.js` 9, 95, 148, 205  (verdict: confirmed)
- **What:** The URL validator regex `/^(https?)|(ipfs):\/\/.*$/` is mis-grouped. Because `|` has lower precedence than concatenation and there is no group around the scheme alternatives, the pattern is really two alternatives: (a) `^(https?)` — matches ANY string that merely STARTS WITH 'http'/'https', with no `://` required; and (b) `(ipfs):\/\/.*$` — matches `ipfs://` appearing ANYWHERE in the string (it is not anchored at start). So values like `"httpsanything garbage"`, `"http"`, or `"foo ipfs://bar"` all pass validation. This regex guards the `icon`/`avatar` (issuer + IOU token) and `url` (URLS/WEBLINKS) fields parsed from third-party trustlist TOML, which are then persisted and served to API consumers.
- **Fix:** Group the scheme alternatives and anchor properly: `/^(https?|ipfs):\/\/.+$/`. Consider also validating with the WHATWG `URL` constructor and an explicit scheme allowlist before storing, since these values are later surfaced to clients.

### [bug/xrpl-protocol] updateTokenAndAccountProps uses array-vs-number comparison that is always truthy
- **File:** `src/ledger/state/mptokenissuance.js` 130-131  (verdict: confirmed)
- **What:** The guard `if (overwriteIssuerNameProp && Object.keys(props) != 0)` compares an array (`Object.keys(props)`) to the number `0`. `Object.keys(props) != 0` coerces the array to a string and is therefore ALWAYS true (even when props is empty, `[] != 0` is false only for the empty array — `[] == 0` is true). Concretely: for an empty props object `Object.keys(props)` is `[]`, and `[] != 0` evaluates to FALSE, so the intended 'props non-empty' check accidentally works for the empty case by coincidence but is incorrect for any non-empty case logic and is clearly not the intended `.length !== 0`. When props is non-empty the condition is true (correct by luck); when metadata parsed to an empty object it is false (correct by luck) — but the expression is semantically wrong and fragile, and `props.issuer_name` may be undefined, writing an undefined issuer name.
- **Fix:** Use `Object.keys(props).length !== 0`, and guard `props.issuer_name` being present before writing the account name prop.

### [improvement/xrpl-protocol] currency UTF-8 validation range terminates at a mangled U+FFFD literal
- **File:** `src/xrpl/tokens.js` 36  (verdict: confirmed)
- **What:** The printable-character filter on the decoded non-standard currency code uses a character-class range whose upper bound is a literal U+FFFD replacement character: the source bytes are `...5c7832302d efbfbd 5d...` i.e. `[\x09\x0A\x0D\x20-�]`. This means a code byte sequence got corrupted in the source at some point and the intended bound (almost certainly 0xFF for a single-byte range, or 0xFFFF) was replaced by U+FFFD. It still functions as a range up to 0xFFFD so it is not a live bug, but it is fragile, non-obvious, and will silently mis-handle any future edit; an embedded replacement char in source is a latent hazard.
- **Fix:** Replace the mangled literal with an explicit escape, e.g. `/^[\x09\x0A\x0D\x20-\u{10FFFF}]*$/u` or the intended `￿`/`\xFF` bound, so the range is unambiguous and edit-safe.


## CROSS-CUTTING (critic, 12)

### [high/efficiency] Entire app runs in one process/event loop with ~15-18 separate read-write better-sqlite3 connections to the same two DB files
- **Where:** `src/lib/workers.js, src/db/index.js, src/crawl/init.js, src/srv/worker.js, src/app/main.js` workers.js:22-52; init.js:13-27; worker.js:7-18,49-56; db/index.js:15-78
- **What:** spawn() (lib/workers.js) is an in-process dynamic import, NOT a worker thread/process. So ledger sync, snapshot, backfill, all 7 crawlers (init.js spawns one openDB per crawler), the 3 HTTP 'workers', and the 2 cache workers ALL run on one event loop and each calls openDB(), opening its own better-sqlite3 connection. That is roughly 15-18 connections to core.db/cache.db inside a single process. better-sqlite3 is synchronous, so there is no real parallelism — the 'worker pool' and busy/ranking logic in worker.js is illusory (mustRunMainThread is meaningless; everything blocks the same thread). Each non-readonly connection also re-runs the createXRP INSERT on open (db/index.js:65-75), and the server query 'workers' open READ-WRITE connections (worker.js:55 calls openDB without coreReadOnly) when they only need reads. Many write connections multiply WAL/statement-cache memory and create needless BEGIN IMMEDIATE lock contention.
- **Fix:** Either (a) make server query workers open coreReadOnly:true connections (they never write), and consolidate background tasks to share a single writer connection so all writes serialize on one connection (eliminating cross-connection BEGIN IMMEDIATE contention), or (b) move to real worker_threads if true parallelism is desired. At minimum, pass coreReadOnly:true for the HTTP workers and avoid running createXRP on every connection.

### [high/bug] BEGIN IMMEDIATE with timeout:600000 across many writer connections can freeze the single thread for up to 10 minutes on lock contention
- **Where:** `src/db/index.js, vendor/structdb/adapters/better-sqlite3.js` db/index.js:53 (timeout:600000); adapter:92-122 (tx uses BEGIN IMMEDIATE)
- **What:** openCoreDB sets timeout:600000 (10 min) and tx() does `connection.exec('BEGIN IMMEDIATE')`. With many read-write connections in the same process (sync, backfill, 7 crawlers, cache todos writer, etc.) all able to take the write lock, if connection A holds the write lock when connection B issues BEGIN IMMEDIATE, better-sqlite3 blocks SYNCHRONOUSLY on the SQLite busy-timeout — and because everything is one thread, that synchronous block freezes the ENTIRE process (HTTP, WS, sync) for up to 600000ms before SQLITE_BUSY would even be raised. Even if steady-state serialization usually avoids a literal collision, any interleaving (e.g. a long write on one connection while another tries to begin) risks a multi-minute total stall rather than a fast failure.
- **Fix:** Drop the busy timeout to a few seconds (or use a single shared writer connection so writes can't contend). A short timeout converts a 10-minute freeze into a fast SQLITE_BUSY that can be retried; better, funnel all writers through one connection.

### [medium/bug] structdb tx() does not await async executors — leaves a transaction open across the event loop and re-throws COMMIT errors as unhandled rejections
- **Where:** `vendor/structdb/adapters/better-sqlite3.js` 92-122
- **What:** When the executor returns a Promise, tx() does NOT await it: it attaches a .then(COMMIT)/.catch(throw) and falls through, returning the pending promise WITHOUT having committed. Two consequences: (1) Between BEGIN IMMEDIATE and the deferred COMMIT, control returns to the event loop with an open transaction; any other code reaching tx() on the same connection sees `connection.inTransaction === true` and runs inline without its own COMMIT, silently interleaving into a foreign transaction. (2) The .catch re-throws inside a promise that has no consumer (the synchronous caller already got the original promise), producing an unhandledRejection. Given main.js wires unhandledRejection -> fatal() -> process.exit, this would crash the whole process. No current caller passes an async executor (all tx callers are synchronous), so this is latent — but it is a footgun that will misbehave the moment an async transaction is introduced.
- **Fix:** Make tx() async-aware: await the executor result before COMMIT/ROLLBACK, and ensure errors reject the returned promise rather than throwing into a dangling .catch. Or explicitly reject async executors as unsupported.

### [medium/efficiency] nodepool seenHashes dedup is an O(n) Array.includes scan over up to 10000 hashes per transaction event
- **Where:** `src/xrpl/nodepool.js` 10,43-51,107-124
- **What:** Every ledger event (one per transaction, per connection) calls sawHash(hash) which does `seenHashes.includes(hash)` — a linear scan of an array kept at up to 10000 entries — then push/shift. For high-throughput ledgers across multiple node connections this is O(n) per tx on the hot path, on the single shared event loop, plus shift() is O(n) too. This is a repeated systemic inefficiency on the ingestion path.
- **Fix:** Use a Set for membership (O(1)) plus a FIFO queue (or a ring buffer / two alternating Sets) to bound size, instead of Array.includes/shift.

### [medium/bug] Crawler prop diffs are split into many separate transactions, exposing partially-applied prop sets to concurrent readers and on crash
- **Where:** `src/db/helpers/props.js` 154-269
- **What:** diffMultiTokenProps/diffMultiAccountProps apply a source's full prop set in DIFF_CHUNK_SIZE-sized chunks, each as its OWN tx(), with `await yieldLoop()` between chunks, and then run sweepStaleProps() (more separate transactions) afterward. The whole diff is logically atomic (replace source X's props) but is committed piecemeal. Because the HTTP server workers and the ledger sync read core.db on other connections concurrently, they can observe a half-updated prop set (new chunk written, stale rows not yet swept, or vice-versa). If the process crashes mid-diff (e.g. another component triggers fatal()), the source's props are left partially updated with no rollback. This is a durability/consistency gap introduced by chunking a conceptually-atomic operation across transactions.
- **Fix:** Document and accept eventual consistency, OR perform the diff+sweep within a single transaction (yielding is then impossible, so chunk only if you accept the consistency tradeoff), OR write to a staging area and swap atomically. At minimum order writes so readers never see fewer props than the previous committed state.

### [medium/bug] Any unhandled rejection in a detached background loop crashes the whole process, including the HTTP server
- **Where:** `src/app/main.js, src/ledger/sync.js, src/xrpl/stream.js, src/cache/worker.js` main.js:45-46; sync.js:30-104; stream.js:148-233; worker.js:60-133
- **What:** Because the whole app is one process, main.js installs process-wide handlers: unhandledRejection -> fatal() -> process.exit(1). The crawl/cache/server apps are launched with a top-level .catch (main.js:63-83), but their real work runs inside DETACHED async IIFEs/loops (sync.js:30 `;(async()=>{...})()`, stream.js:188 filler workers, cache/worker.js:60/142 worker loops) whose rejections are NOT captured by those top-level catches. So an error thrown inside the sync tx loop, a filler worker, or a cache worker becomes an unhandledRejection and exits the ENTIRE process — taking the HTTP/WS server down with it. The 'attempting to continue without it' resilience comments are misleading: a background subsystem failure is not isolated from the user-facing server.
- **Fix:** Wrap each detached background loop in its own try/catch that logs and either restarts the loop or degrades gracefully, so a single subsystem failure does not invoke the global unhandledRejection->exit path and kill the server.

### [low/bug] markSyncOperation/endSyncOperation is a single global clobbered by concurrent in-process tasks
- **Where:** `src/lib/health.js` 18-43
- **What:** currentSyncOp/currentSyncOpStartedAt are single module-global values. Since sync, backfill, both cache workers, crawlers, and the 6+ concurrent openDB timeStage() calls at startup all call markSyncOperation()/endSyncOperation() on the same event loop, they overwrite each other. endSyncOperation() from one task clears the marker another task just set; withSyncOp() blocks nest/overlap. The stall-attribution log (health.js:78-84) therefore frequently reports the wrong operation or 'no sync op marked'. This is the systemic generalization of the already-confirmed 'unbalanced on error path' finding: even on the happy path the global is unreliable under the app's actual concurrency.
- **Fix:** Track operations as a counted stack or a Map keyed by an operation id, or accept that attribution is best-effort and document it. At minimum avoid endSyncOperation() unconditionally nulling a marker another task owns.

### [low/bug] nodepool request() leaves timed-out requests in the queue; a perpetually-unbiddable request is never removed and may still execute
- **Where:** `src/xrpl/nodepool.js` 16-41,137-178
- **What:** request() rejects after a 30s timeout but the request object remains in `queue`; it is only spliced out (line 36) when a node bids >0 and accepts it. If a node later bids, the workQueue still calls node.do() for the already-rejected request (wasted RPC, result/resolve is a no-op). If no node ever bids (e.g. the requested ledger range is never available), the entry stays in `queue` forever, and workQueue keeps re-scanning it every 100ms — a slow leak plus wasted CPU. The timeout path should remove the request from the queue.
- **Fix:** On timeout, mark the request cancelled and splice it from queue (or have workQueue skip/drop cancelled requests). Track a cancelled flag checked before node.do().

### [low/efficiency] Crawler schedulers write one un-batched, un-transacted operations row per item (N+1 synchronous writes on the shared loop)
- **Where:** `src/crawl/schedule.js` 155-165,186-199
- **What:** scheduleIterator.markDone and scheduleBatchedIterator.flush each call ctx.db.core.operations.createOne() once per processed item, each a separate synchronous write with no enclosing transaction. Across 7 crawlers iterating tens of thousands of items (collectItemIds comments reference 74k-item crawls), this is a large number of individual SQLite writes blocking the single event loop, each also doing createOne's existence read-then-insert. Batching these into a single transaction per flush would cut write/fsync amplification dramatically.
- **Fix:** Wrap each flush's operation inserts in a single ctx.db.core.tx() and/or use a bulk insert, instead of per-item createOne outside any transaction.

### [low/improvement] WS manager and HTTP rate-limit setInterval timers are never cleared/unref'd and the ws keep-alive interval leaks on shutdown
- **Where:** `src/srv/ws.js, src/srv/server.js` ws.js:14-28; server.js:15-49
- **What:** createManager() starts a setInterval keep-alive loop (ws.js:14) that is never stored or cleared and is not .unref()'d; createRateLimitMiddleware keeps a Map of per-IP buckets swept lazily. Neither is torn down on shutdown. Combined with terminate()/SIGINT calling process.exit() immediately (already flagged in bootstrap-lib), these timers/maps simply die with the process, but while running, the keep-alive interval iterates the clients array which — due to the confirmed splice() bug — can retain dead client objects, so the interval keeps pinging/closing leaked sockets. ### [low/bug] Cross-connection todos write/delete race on cache.db between the sync transaction and the cache workers
- **Where:** `src/cache/todo.js, src/cache/worker.js, src/ledger/sync.js` todo.js:12-17,46-53; worker.js:68,112,148,169; sync.js:38-63
- **What:** During each ledger, the sync core.db transaction calls markCacheDirtyForTokenMetrics/Props which do ctx.db.cache.todos.createOne — writes to cache.db on the SYNC process's cache connection, INSIDE the core.db tx but on a different DB file (so not covered by that transaction's atomicity). Meanwhile the two cache workers read+delete todos on their own cache.db connections. createOne's existence-check-then-insert is not atomic across connections, and the worker's readOne/deleteOne can interleave with the sync writer. With WAL this mostly serializes, but the design relies on the [task,subject] unique to dedup; a delete-by-worker that races with a create-by-sync can drop a freshly-needed todo (worker deletes the row it just processed while sync re-inserts the same (task,subject) for a newer change — the new dirty mark is then lost if ordering is unlucky). Worth auditing as a missed-update window in the cache-invalidation path.
- **Fix:** Process todos with a claim pattern (e.g. mark in-progress, re-check a dirty epoch, or delete only rows whose id matches the one read) so a concurrent re-dirty during processing is not lost; or re-mark dirty atomically with the data change.

### [low/improvement] isLoopCritical/load-shedding decisions are based on a single 250ms lag sample and reflect past blocking, not the current synchronous request
- **Where:** `src/lib/health.js, src/srv/http.js` health.js:111-117; http.js:450-462
- **What:** Load shedding in http.handle() checks isLoopCritical() which reads lastLagMs — a single most-recent 250ms sample. Because every API query executes synchronously (better-sqlite3) on the shared loop, the expensive request itself (e.g. the already-flagged 100k-row token list) blocks the loop AFTER the shed check has passed; the lag sample that would reflect it only updates afterward. So the mechanism cannot prevent the very requests most likely to cause stalls — it only sheds requests that arrive after an unrelated block has already started. This is a structural limitation of doing synchronous DB work on the request thread; the noteHttpRequestStart/End counter and the cache workers' load-aware backoff are the only real levers and they only throttle background work, not concurrent API queries.
- **Fix:** Bound per-query cost at the source (cap limits/points — partly filed) and consider sampling lag more frequently or tracking in-flight synchronous query duration; document that load shedding is reactive, not predictive, given the synchronous DB model.
